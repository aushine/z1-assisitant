# 03 · 习惯与待办二级分类（R3）

> **性质**：需求（非 bug）｜**端**：双端｜**优先级**：P0（本批最重）
> **推翻原决策**：`md/spec/03-数据模型.md` §5.2 / `06 §5` / `07 §4` 原写「只做一级（D21）」，
> 本批改为**两级**。落地后须回写这几处。

---

## 1. 是什么

把习惯 / 待办的分类从**一级平铺**升级为**两级**，形态对齐**财务分类 `finance_categories`**：

```
习惯域（domain=habit）              待办域（domain=task）
  运动 sport                          工作 c_work
   ├─ 羽毛球  sport_01                  ├─ 周报   c_work_01
   ├─ 跑步    sport_02                  └─ 会议   c_work_02
   └─ 骑行    sport_03                 学习 c_study
  饮食 diet                             ├─ 课程   c_study_01
   ...                                  └─ 阅读   c_study_02
```

- 一级：内置 4（habit）/ 6（task），**保留旧 id**（`sport` / `c_work`…）
- 二级：**内置种子**（本批新增）+ **用户可自己添加/删除**
- 用户未选二级时，行为等同现状（只挂一级）

---

## 2. 信息架构

| 场景 | 一级 | 二级 |
|---|---|---|
| 新建/编辑习惯 | 必选（现状不变） | 可选；一级有二级时才出现 |
| 新建/编辑待办 | 必选（现状不变） | 可选 |
| 分类管理 | 显示一级列表，每个一级可展开看二级 | 增删改 |
| 统计（按分类分组） | 二级归集到一级 | 二级不单独成组 |

> 与财务分类的差异：财务是**记一笔时选二级**（表单内联平铺 + 点一级弹二级）；
> 习惯/待办的选择频率低（spec D21 原话），因此**二级选择放在「已选一级」之后按需展开**，
> 不做财务那种常驻平铺（见 §5 交互）。

## 3. 数据模型（`user_categories`）

### 3.1 表结构改动

沿用现有表，**新增 `parent_id` 列**（`md/spec/03` 已注明"表结构预留 parent_id"）：
实际现有 model 无该字段，本批补上。对齐 `finance_categories` 的既有范式：

| 列 | 类型 | 说明 |
|---|---|---|
| `parent_id` | `varchar(32) NOT NULL DEFAULT ''` | **空串 = 一级**（⚠️ 不能 NULL，唯一索引里 NULL 不参与比较） |
| `full_name` | `varchar(80) NULL` | 完整名（「运动-跑步」）；选择器展示 / 搜索用 |
| `full_name` 说明 | — | ⚠️ 二级若留空，读时用「父名-子名」拼接兜底 |

**唯一索引调整**（⚠️ 血泪纪律，参考 `finance_categories`）：

```
原：uk_user_cat (user_id, domain, name, deleted_seq)
新：uk_user_cat (user_id, domain, parent_id, name, deleted_seq)
```

- 加 `parent_id` 作为第 3 列，让「同域不同父下可同名」（如 task 下两个「其他」分属不同父）。
- ⚠️ **索引 tag 必须显式写名**且与 DDL 逐字一致，否则 AutoMigrate 误删索引 → `Error 1553`。
- ⚠️ DDL **双副本同步**：`db/init.sql` + `manifest/sql/0001_init.sql`（+ `deploy/sql/`）。

### 3.2 复合主键不变

`(id, user_id)` 保持（内置 id 跨用户重复，见 model 注释铁律）。

### 3.3 id 规则

| 类型 | 规则 | 示例 |
|---|---|---|
| 内置一级 | 保留旧值 | `sport` / `c_work` |
| **内置二级** | `<父id>_NN`（NN 从 01 起） | `sport_01` / `c_work_01` |
| 用户新建一级/二级 | `uc_<domain>_<10位随机>` | `uc_habit_a1b2c3d4e5` |

> ⚠️ 用户新建的二级**不加父前缀**，用统一的 `uc_` 随机规则（避免与内置 `<父id>_NN` 撞）。

## 4. 内置种子（`utility/user_category_seed.go`）

### 4.1 种子结构扩展

`UserCategorySeed` 增加 `ParentID` 字段。**不写进 SQL**（用户级、懒创建幂等播种）。

### 4.2 内置二级清单（草案，实施前定稿）

**习惯域（domain=habit）**

| 父（一级） | 二级 |
|---|---|
| 运动 `sport` | 跑步 / 骑行 / 羽毛球 / 健身 / 游泳 |
| 饮食 `diet` | 早餐 / 午餐 / 晚餐 / 控糖 / 喝水 |
| 生活 `life` | 早起 / 早睡 / 整理 / 记账 |
| 学习 `study` | 阅读 / 背单词 / 课程 / 复盘 |

**待办域（domain=task）**

| 父（一级） | 二级 |
|---|---|
| 工作 `c_work` | 周报 / 会议 / 汇报 / 对接 |
| 学习 `c_study` | 课程 / 阅读 / 练习 |
| 生活 `c_life` | 采购 / 家务 / 缴费 |
| 健康 `c_health` | 就医 / 运动 / 体检 |
| 社交 `c_social` | 聚会 / 联络 / 送礼 |
| 其他 `c_other` | （无二级，保持平铺） |

- 图标：**每个内置二级配独立 lucide 图标**（参考财务 85 个二级都有独立 icon 的做法；名字须在两端 `ICON_GROUPS` 内真实存在）。
- tint / emoji：二级留空 → **继承父级**（与财务一致）。
- sort：一级 10/20/30…；二级在其父下 10/20/30…。

> ⚠️ 图标名必须逐一核对 `constants/icon-groups.ts`（两端各一份，逐字一致 + SHA256 校验）。

## 5. 交互设计

### 5.1 移动端

**选择分类（新建/编辑习惯、待办）**
```
[ 一级 chip 行：运动 | 饮食 | 生活 | 学习 ]      ← 现状，默认不选中
     ↓ 点击「运动」
[ 二级行展开：不限 | 跑步 | 骑行 | 羽毛球 | 健身 | 游泳 ]
     ← 首项「不限」= 只记一级（对齐财务「只记大类」）
     ← 一级若无二级，不出现二级行
```

**分类管理（我的 → 分类管理）**
- 一级列表，每个一级右侧 `ChevronRight`；有二级的可展开。
- 二级支持增删改（见 04 文档）。
- 长按/右键增删（对齐财务 `useLongPress` 500ms / 桌面右键 Dropdown）。

### 5.2 桌面端

- 一级 chip 行 + hover 浮出二级面板（对齐财务 `08 §8` 桌面交互）。
- 分类管理：`Tree` 或可展开表格（一级行 + 缩进二级行）。

## 6. 接口

复用现有 `/user-categories` 端点，**扩展字段**（不新增端点）：

| 方法 | 路径 | 改动 |
|---|---|---|
| `GET` | `/z1/api/v1/user-categories?domain=habit\|task` | 响应 `items[]` 增加 `parent_id` / `full_name`；**返回扁平全量**（一级+二级），前端自行组树 |
| `POST` | `/z1/api/v1/user-categories` | 请求体增加 `parent_id`（可选，空=一级）；二级校验：父必须存在、父必须是一级、同一父下不重名 |
| `PATCH` | `/z1/api/v1/user-categories/:id` | 可改名/图标；**不允许改 parent_id / domain**（沿用现状：domain 不可改） |
| `DELETE` | `/z1/api/v1/user-categories/:id` | 软删三件套 `is_deleted=1 + deleted_at + deleted_seq`；⚠️ **删一级时其下二级怎么办** → 见 §7 |

**响应结构（草案）**
```jsonc
{
  "seeded": true,
  "items": [
    { "id": "sport", "domain": "habit", "parent_id": "", "name": "运动",
      "full_name": "运动", "icon": "lucide:Dumbbell", "tint": "success", "sort": 10, "is_builtin": true },
    { "id": "sport_01", "domain": "habit", "parent_id": "sport", "name": "跑步",
      "full_name": "运动-跑步", "icon": "lucide:Footprints", "tint": "success", "sort": 10, "is_builtin": true }
  ]
}
```

## 7. 关键规则

| # | 规则 | 说明 |
|---|---|---|
| **R3-1** | **删除一级** | 该一级下若有**被引用的二级**（有习惯/待办挂在其上），拒绝删除或级联软删二级。**推荐**：提示「该分类下有 N 个二级/记录」，用户确认后**级联软删**二级，挂在这些分类上的习惯/待办 `category_id` **置空或保留**（见 R3-2）。 |
| **R3-2** | **存量引用** | `habits.category` / `tasks.category_id` 存的是**分类 id**。二级也有 id，所以无需改字段。⚠️ 但**统计分组 SQL** 必须能处理二级（见 R3-3）。 |
| **R3-3** | **统计归集** | 任何按 `category` 分组的统计，必须**含子分类归集**：`category_id = ? OR category_id IN (SELECT id FROM user_categories WHERE parent_id = ?)`。否则给一级看板却记在二级上，永远显示 0。⚠️ 参考财务 `SumExpenseByCategory` 的教训。 |
| **R3-4** | **历史数据迁移** | 见 §8。 |
| **R3-5** | **懒创建播种** | 判断「是否播种」仍是「存在 `is_builtin=1` 的行（含已删）」；新增二级后，**老用户**（已播种过）不会自动获得新二级 → 需要**迁移脚本**补种（见 §8）。 |

## 8. 历史数据迁移（⚠️ 数据库在 Pi，本地=线上同一库）

### 8.1 要迁什么

1. **加列**：`user_categories.parent_id`、`full_name`（DDL 双副本同步）。
2. **换唯一索引**：`uk_user_cat` 加 `parent_id` 列（先 DROP 旧索引再建新，注意 `Error 1553`）。
3. **补种内置二级**：对**已存在 `user_categories` 行**的所有用户，按 domain 补插内置二级（`INSERT IGNORE`，幂等）。

### 8.2 迁移纪律（照抄 `md/spec/03 §8`）

- ⚠️ 跑 SQL 用 **`scripts/sqlrun/main.go`**，**不要用 `init_db.go`**（失败只记日志）。
- ⚠️ **共享库清理先 SELECT 白名单**再逐条操作（本地=线上）。
- ⚠️ **脚本必须幂等**：可重跑，重跑影响行数应为 0。
- ⚠️ **归档先于删除**。
- DDL 双副本 + 检查 `dao/db.go` AutoMigrate。

### 8.3 执行方式

1. 迁移脚本放 `life-assisitant-api/scripts/`（参考 `scripts/fincatseed` 的写法）。
2. 我（agent）通过 `ssh pi` 在 Pi 上执行（库在 Pi：`192.168.101.75:4417`）。
3. 执行前**先 SELECT 确认白名单**，执行后**复查行数**。
4. ⚠️ 上线顺序：**先迁库 → 再部署新代码**（否则新代码查 `parent_id` 列不存在会报错）。
