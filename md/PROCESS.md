## 1. 全流程概览

```
① 需求阶段          ② 开发阶段             ③ 验收阶段              ④ 上线
用户提需求     →   罗格依 spec 开发   →  主理人检测 schedule 全勾 → 自动构建部署
主理人定稿         提交代码 + 勾选       主理人核验交付物          飞书群 @用户 通知
输出 spec+schedule  schedule.md          不过则打回（改 schedule）
```

### 三个阶段与计时口径

| 阶段 | 起点 | 终点 | 计时字段 |
|---|---|---|---|
| **需求阶段** | 用户开始与主理人讨论该需求（首条相关消息时刻） | 主理人交付 spec + schedule（push 完成） | `t_req_start` → `t_spec_delivered` |
| **开发阶段** | spec/schedule 交付（同上） | 罗格提交使 schedule **全部勾选完成**的 commit 时刻 | `t_spec_delivered` → `t_dev_done` |
| **验收阶段** | 主理人检测到 schedule 全勾（`t_dev_done`） | 主理人核验 + 构建部署完成 | `t_dev_done` → `t_deploy_done` |

> **总用工耗时** = 三段之和。上线通知里须分别列出三段耗时 + 总计。

## 2. 需求识别（主理人自主判断）

用户用自然语言表达需求，主理人**自主判断意图**。典型触发：

- 「加一个 xx 按钮」「增加一个 xx 模块」「xx 改成 xx」
- 「这里应该能 xx」「希望 xx 支持 xx」
- 明确的 bug 反馈 / 体验问题

**判断后**：
- **小 bug / 一致性修改**（能顺手改、上升不到"需求"）→ 按 `md/spec/` 铁律**可直接改**，但仍需在当批 spec 目录归档留痕。
- **需要修改代码的"需求"** → **必须先设计 spec + schedule 再动手**。

> ⚠️ 主理人**不写代码**：小 bug 也走"输出 spec+schedule → 罗格改"的路径（除非用户特别指示）。

## 3. 目录与命名规范

### 3.1 spec 目录

```
md/
└── spec-yyyyMMdd-vX/          ← X = 当天第几批需求，从 v1 起递增
    ├── README.md              ← 批次总览（范围、决策留档、验收标准）
    ├── schedule.md            ← 【必须，与 spec 同级】任务清单（开发完成时全勾）
    ├── 01-xxx.md              ← 分项设计文档
    ├── 02-xxx.md
    └── ...
```

- `yyyyMMdd` = **当天日期**（北京时间）。
- `X` = **当天第几批**，从 `v1` 开始递增（当天第 2 批 = `v2`）。
- **未验收不上新版本号**；验收通过后才开下一批。

### 3.2 spec 文档风格

沿用现有 `md/spec-20260924-v1/` 的风格：
是什么（问题/需求）→ 改动方案 → 关键规则 → 接口/改动清单 → 端差异（双端覆盖）→ 验收标准。

### 3.3 完成信号（2026-10-01 二次拍板：**分支内完成**）

> **开发完成的唯一判定信号，状态机只认它（不靠扫 schedule 复选框）。**
> **重要变更（2026-10-01 晚）**：开发在 **feature 分支**上做，完成信号发在 **main**，二者要配合。

#### 3.3.0 分支约定（新）

| 对象 | 放哪 | 说明 |
|---|---|---|
| **spec 目录** `md/spec-yyyyMMdd-vX/` | **只在 main** | 需求/设计是主理人下发的，**绝不在分支里建/改 spec 目录**。罗格直接从 main 读。 |
| **代码** | **feature 分支** | 罗格为代码改动建分支，如 `T-00x-<slug>`，**不直接推 main**。 |
| **完成信号 + schedule 勾选** | **main** | 罗格完成后，**把这两样提交到 main**（见流程），让主理人状态机能在 main 上监测到。 |

> 为什么要拆：spec 是「下发物」，代码是「交付物」，混在一个分支里会让主理人看不到进度；
> 而完成信号必须落在 main，状态机才监测得到。

#### 3.3.1 完成信号：目录改名 + schedule 头部写明分支 ⭐

**开发工程师（罗格）在代码全部提交到 feature 分支、schedule.md 全部勾选后，在 `main` 上执行两件事：**

**① 在 `schedule.md` 文件开头（标题下方）加一行完成声明**，格式固定、便于状态机解析：

```markdown
# Schedule · spec-20261001-v2

> **完成声明**：已在分支 `T-003-schedule` 完成

> **批次**：spec-20261001-v2
...
```

- 格式固定为：`> **完成声明**：已在分支 \`<分支名>\` 完成`（反引号包分支名）。
- 分支名 = 代码所在 feature 分支的真实名字（如 `T-003-schedule`）。
- 这一行是**主理人状态机判定「开发完成 + 去哪个分支取代码」的唯一依据**。

**② 给 spec 目录改名加 `(√)`**（**在 main 上**）:

```bash
# 在 main 分支上：
git checkout main
git pull
# ① 改 schedule.md，加「完成声明：已在分支 T-00x-xxx 完成」
# ② 目录改名
git mv md/spec-20261001-v2 "md/spec-20261001-v2(√)"
git commit -m "chore: spec-20261001-v2 开发完成（分支 T-00x-xxx，标记 (√)）"
git push    # ← 推到 main
```

- 后缀为**全角** `(√)`（全角括号 + 全角根号）。
- **只有罗格改名 + 写完成声明**，主理人不代改。
- 主理人状态机在 **main** 上检测到带 `(√)` 的 spec 目录 → **读 schedule 头部的完成声明拿到分支名 → 切到该分支取代码做验收**。
- `schedule.md` 复选框**仍保留**（供人看进度），但**不作为状态机判定**。

#### 3.3.2 主理人验收后的合并

- 主理人核验**分支代码**通过 → **合并 feature 分支到 main**（或由罗格按主理人指令合）→ 再部署。
- 若打回：罗格按打回原因在分支上修正，**重提交时再次确保** ①schedule 头部完成声明与分支名一致 ②目录带 `(√)`。

### 3.4 铁律（沿用）

1. **默认双端覆盖**：除非特别说明，改动同时出移动端 + 桌面端方案。
2. **不确定先问**：设计阶段有歧义先与用户确认，留档在 README 的「决策留档」。
3. **验收后回写**：本批验收通过后，结论回写 `md/spec/` 对应章节。

## 4. schedule.md 格式规范

> ⚠️ **2026-10-01 更新**：完成判定改为「spec 目录名带 `(√)`」+「schedule 头部写完成声明」（见 §3.3）。
> schedule.md 复选框仍保留（供人看进度），**状态机不再解析复选框**，但**完成声明行是状态机读取分支名的依据**。

```markdown
# Schedule · spec-yyyyMMdd-vX

> **完成声明**：已在分支 `<branch-name>` 完成   ← 逗清后再加；仅一行；分支名用反引号包住

> **批次**：spec-yyyyMMdd-vX
> **状态**：开发中 / 已完成
> **交付物**：一句话说明本批要交付什么

## 任务清单

- [ ] **T1** · 任务标题
  - 文件：`path/to/file`
  - 改动：简述要点
  - 验收：怎么算完成
- [x] **T2** · 任务标题
  - ...

## 完成判定

（以下两项由罗格在代码提交后勾选，全部勾选则视为本批开发完成）

- [ ] 所有任务项已实现并 commit
- [ ] 本批 spec 中「验收标准」逐条自测通过
```

### 解析规则

- 任务项：`- [ ] **Tn** ·` / `- [x] **Tn** ·`（支持 `- [X]`）。
- **完成声明行（关键）**：正则 `完成声明\**：已在分支\s*`([^`]+)`` —— 状态机据此取到**分支名**。
- 罗格完成开发后（在 main 上）：① 所有复选框改 `- [x]`；② 在文件头加**完成声明**；③ 给 spec 目录加 `(√)` 后缀。

## 5. git 状态机（主理人自动执行）

### 5.1 触发（与 git 平台解耦）

- **主通道（实时）**：git 服务器的 `post-receive` hook / webhook → POST 到 VPS 接收端点 → 立即跑状态机。
  - 任何 git 平台都支持（GitHub / Gitea / GitLab / 自建裸仓库），**不绑定 GitHub 云服务**。
- **兜底（准实时）**：cron 轮询（VPS，当前每 10 分钟，可缩短）。
- 两种方式调用**同一个**状态机脚本，逻辑零分叉。

### 5.2 判定流程

```
1. fetch / 收到 push 事件（监测 main）
2. 找「当前活跃 spec」= md/ 下日期最新 + 版本号最大的 spec-yyyyMMdd-vX 目录
3. 检查目录名是否带 (√)
   ├─ 不带 (√) → 开发中，静默退出
   └─ 带 (√)   → 进入【验收阶段】
4. 读该批次 schedule.md 头部的「完成声明」行 → 取到 feature 分支名（如 T-00x-xxx）
5. 核验（在 feature 分支上取代码）：
   a. git fetch 后，对照 schedule 每个任务项，检查分支上对应代码文件是否真的改了
   b. 对照 spec README 的「验收标准」逐条核对
   ├─ 全部通过 → 合并分支到 main → 步骤 6
   └─ 有未达标 → 【打回】：改 schedule.md 完成声明行（标 ❓ 并写原因）/ 把未完成项改回 - [ ] → **去掉目录名里的 (√)** → 在 main 上 commit → push → 通知群
6. 构建 + 部署到 Pi（vps-deploy.sh → ssh pi "/opt/z1-deploy/pi-build-deploy.sh all"）
7. 部署校验通过 → 飞书群 @用户 通知（含三段耗时）
8. 记录状态到状态机状态文件（防重复触发）
```

> **关键**：代码在 feature 分支，完成信号在 main。状态机只看 main，但**必须根据完成声明去分支取代码验收**，不能只看 main 的代码。

### 5.2.1 CI 不再自动部署（2026-10-01 起）

- `ci-cd.yml` 的 **deploy job 已关闭自动触发**：push 只跑 build（检查+编译+打包），**不部署**。
- 部署**只由主理人**在核验通过后执行（自动：状态机；手动应急：`workflow_dispatch` 勾 `deploy_now`）。
- 确保「**核验通过才上线**」，且部署入口可迁到自建 CI。

### 5.3 防重复触发（幂等）

- 状态机落盘一个状态文件（如 `scripts/.z1-fsm-state.json`），记录**已处理过的 commit sha** 与**当前批次状态**（`developing` / `verifying` / `deployed`）。
- 同一 commit / 同一批次不重复部署。
- 部署成功后才把批次标记为 `deployed`；失败的批次需人工介入（不自动重试，避免炸生产）。

### 5.4 部署

- 部署命令：`ssh pi "/opt/z1-deploy/pi-build-deploy.sh all"`（详见 `PI-ACCESS.md`）。
- **部署前**：确保工作区干净、`origin/main` 已是最新。
- **部署后**：核对产物 hash / HTTP 200 自检。

## 6. 上线通知（飞书群）

部署成功后，主理人在飞书群发通知，**@用户**，格式：

```
🚀 上线通知｜<批次名>（spec-yyyyMMdd-vX）

上线功能：
- <功能1>
- <功能2>

⏱️ 用工耗时：
- 需求阶段：X 小时 Y 分（t_req_start → t_spec_delivered）
- 开发阶段：X 小时 Y 分（t_spec_delivered → t_dev_done）
- 验收阶段：X 分 Y 秒（t_dev_done → t_deploy_done）
- ⛓️ 总计：X 小时 Y 分

📦 部署：<commit sha> · <部署自检结果>
```
