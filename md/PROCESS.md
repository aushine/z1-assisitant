## 1. 全流程概览

```
① 需求阶段          ② 开发阶段             ③ 验收阶段              ④ 上线
用户提需求     →   罗格依 spec 开发   →  主理人检测 schedule 全勾 → 自动构建部署
主理人定稿         提交代码 + 勾选       主理人核验交付物          飞书群 @用户 通知
输出 spec+schedule  schedule.md          不过则打回（改 schedule）
```

### 三个阶段与计时口径

| 阶段 | 起点 | 终点 | 计时字段 |
|---|---|---|---|
| **需求阶段** | 用户开始与主理人讨论该需求（首条相关消息时刻） | 主理人交付 spec + schedule（push 完成） | `t_req_start` → `t_spec_delivered` |
| **开发阶段** | spec/schedule 交付（同上） | 罗格提交使 schedule **全部勾选完成**的 commit 时刻 | `t_spec_delivered` → `t_dev_done` |
| **验收阶段** | 主理人检测到 schedule 全勾（`t_dev_done`） | 主理人核验 + 构建部署完成 | `t_dev_done` → `t_deploy_done` |

> **总用工耗时** = 三段之和。上线通知里须分别列出三段耗时 + 总计。

## 2. 需求识别（主理人自主判断）

用户用自然语言表达需求，主理人**自主判断意图**。典型触发：

- 「加一个 xx 按钮」「增加一个 xx 模块」「xx 改成 xx」
- 「这里应该能 xx」「希望 xx 支持 xx」
- 明确的 bug 反馈 / 体验问题

**判断后**：
- **小 bug / 一致性修改**（能顺手改、上升不到"需求"）→ 按 `md/spec/` 铁律**可直接改**，但仍需在当批 spec 目录归档留痕。
- **需要修改代码的"需求"** → **必须先设计 spec + schedule 再动手**。

> ⚠️ 主理人**不写代码**：小 bug 也走"输出 spec+schedule → 罗格改"的路径（除非用户特别指示）。

## 3. 目录与命名规范

### 3.1 spec 目录

```
md/
└── spec-yyyyMMdd-vX/          ← X = 当天第几批需求，从 v1 起递增
    ├── README.md              ← 批次总览（范围、决策留档、验收标准）
    ├── schedule.md            ← 【必须，与 spec 同级】任务清单（状态机判定依据）
    ├── 01-xxx.md              ← 分项设计文档
    ├── 02-xxx.md
    └── ...
```

- `yyyyMMdd` = **当天日期**（北京时间）。
- `X` = **当天第几批**，从 `v1` 开始递增（当天第 2 批 = `v2`）。
- **未验收不上新版本号**；验收通过后才开下一批。

### 3.2 spec 文档风格

沿用现有 `md/spec-20260924-v1/` 的风格：
是什么（问题/需求）→ 改动方案 → 关键规则 → 接口/改动清单 → 端差异（双端覆盖）→ 验收标准。

### 3.3 铁律（沿用）

1. **默认双端覆盖**：除非特别说明，改动同时出移动端 + 桌面端方案。
2. **不确定先问**：设计阶段有歧义先与用户确认，留档在 README 的「决策留档」。
3. **验收后回写**：本批验收通过后，结论回写 `md/spec/` 对应章节。

## 4. schedule.md 格式规范（状态机契约）

> ⚠️ **本格式是 git 状态机的解析契约，改动需同步更新状态机脚本。**

```markdown
# Schedule · spec-yyyyMMdd-vX

> **批次**：spec-yyyyMMdd-vX
> **状态**：开发中 / 已完成
> **交付物**：一句话说明本批要交付什么

## 任务清单

- [ ] **T1** · 任务标题
  - 文件：`path/to/file`
  - 改动：简述要点
  - 验收：怎么算完成
- [x] **T2** · 任务标题
  - ...

## 完成判定

（以下两项由罗格在代码提交后勾选，全部勾选则视为本批开发完成）

- [ ] 所有任务项已实现并 commit
- [ ] 本批 spec 中「验收标准」逐条自测通过
```

### 解析规则（状态机用）

- **任务项**：形如 `- [ ] **Tn** ·` / `- [x] **Tn** ·`（支持 `- [X]`）。
- **完成判定**：`# Schedule` 之后、文件内**所有**复选框 `- [ ]` 均变为 `- [x]` ⇒ 视为**开发完成**。
- 用 `grep -c '^- \[ \]'` 计数未完成项；为 0 则全勾。

## 5. git 状态机（主理人自动执行）

### 5.1 触发

- **cron 轮询**（VPS 上，默认每 10 分钟）：`git fetch` → 检测 `origin/main` 是否有新 commit。

### 5.2 判定流程

```
1. fetch 到新 commit
2. 找「当前活跃 spec」= md/ 下日期最新 + 版本号最大的 spec-yyyyMMdd-vX 目录
3. 读该目录的 schedule.md
4. 统计未勾选项（- [ ] 计数）
   ├─ > 0  → 开发中，什么都不做（静默）
   └─ = 0  → 进入【验收阶段】
5. 验收核验：
   a. 对照 schedule 每个任务项，检查对应代码文件是否真的改了（git diff / 文件内容）
   b. 对照 spec README 的「验收标准」逐条核对
   ├─ 全部通过 → 步骤 6
   └─ 有未达标 → 【打回】：修改 schedule.md 把未完成项改回 - [ ]（并在项下加「❌ 打回原因」）→ commit → push → 通知群
6. 构建 + 部署到 Pi：ssh pi "/opt/z1-deploy/pi-build-deploy.sh all"
7. 部署校验通过 → 飞书群 @用户 通知（含三段耗时）
8. 记录状态到状态机状态文件（防重复触发）
```

### 5.3 防重复触发（幂等）

- 状态机落盘一个状态文件（如 `scripts/.z1-fsm-state.json`），记录**已处理过的 commit sha** 与**当前批次状态**（`developing` / `verifying` / `deployed`）。
- 同一 commit / 同一批次不重复部署。
- 部署成功后才把批次标记为 `deployed`；失败的批次需人工介入（不自动重试，避免炸生产）。

### 5.4 部署

- 部署命令：`ssh pi "/opt/z1-deploy/pi-build-deploy.sh all"`（详见 `PI-ACCESS.md`）。
- **部署前**：确保工作区干净、`origin/main` 已是最新。
- **部署后**：核对产物 hash / HTTP 200 自检。

## 6. 上线通知（飞书群）

部署成功后，主理人在飞书群发通知，**@用户**，格式：

```
🚀 上线通知｜<批次名>（spec-yyyyMMdd-vX）

上线功能：
- <功能1>
- <功能2>

⏱️ 用工耗时：
- 需求阶段：X 小时 Y 分（t_req_start → t_spec_delivered）
- 开发阶段：X 小时 Y 分（t_spec_delivered → t_dev_done）
- 验收阶段：X 分 Y 秒（t_dev_done → t_deploy_done）
- ⛓️ 总计：X 小时 Y 分

📦 部署：<commit sha> · <部署自检结果>
```
